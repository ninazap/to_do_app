## 2. Краткое описание проекта

Проект *to_do_app* представляет собой полноценное RESTful-приложение для управления персональными задачами, разработанное командой студентов в рамках дисциплины «Проектный практикум 1».  
Основной технологический стек:
- **Backend**: FastAPI (Python)  
- **База данных**: PostgreSQL  
- **Контейнеризация**: Docker + Docker Compose  
- **Управление зависимостями**: Poetry  
- **Миграции**: Alembic  
- **Тестирование**: pytest + httpx  

Функциональность включает:
- Регистрацию и авторизацию пользователей;
- Управление задачами (CRUD);
- Категоризацию, фильтрацию, пагинацию и сортировку;
- Поддержку светлой и тёмной тем оформления;
- Интеграцию с внешним API (Google Tasks).

Архитектура проекта следует принципам разделения ответственности: модели, схемы, CRUD-операции и маршруты реализованы в отдельных модулях, что способствует поддерживаемости и тестируемости кода.

## 3. Мой вклад в проект

В проекте я выполнила роль **инженера по обеспечению качества (QA)** с фокусом на **автоматизированное функциональное и интеграционное тестирование REST API**.

### 3.1. Область ответственности

Основные задачи, выполненные в рамках моего вклада:

- **Разработка и поддержка тестового покрытия** для ключевых эндпоинтов:
  - `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/change-password`;
  - `/tasks/` (CRUD, фильтрация по статусу/категории, пагинация);
  - `/categories/`;
  - обработка ошибок валидации и авторизации.
  
- **Проектирование тест-кейсов** с учётом:
  - позитивных и негативных сценариев;
  - граничных значений (например, максимальная длина заголовка задачи);
  - конфликтов состояний (например, удаление несуществующей задачи);
  - межмодульных зависимостей (связь пользователя ↔ задача ↔ категория).

- **Интеграция тестовой инфраструктуры**:
  - использование фикстур `pytest` для изоляции тестов;
  - применение `httpx.AsyncClient` для выполнения запросов к FastAPI-приложению;
  - настройка отдельной тестовой базы данных через override-конфигурацию в `conftest.py`;
  - запуск тестов внутри Docker-контейнера командой:  
    ```bash
    docker-compose exec app poetry run pytest
    ```

- **Коммуникация с командой**:
  - участие в ежедневных синхронизациях (ad-hoc standups);
  - фиксация найденных несоответствий в устной форме и через GitHub-issues;
  - проверка исправлений после внесения изменений разработчиками.

### 3.2. Результаты

В результате проделанной работы:
- Достигнуто **покрытие >85%** основных API-методов;
- Выявлено и устранено **7 функциональных несоответствий**, включая:
  - отсутствие валидации email при регистрации;
  - некорректную обработку дубликатов категорий;
  - уязвимость к CSRF в эндпоинте смены пароля (теоретически, без фронтенда — не критично, но зафиксировано);
- Сформирован **повторяемый и изолированный тестовый контур**, готовый к расширению.

## 4. Использованные технологии и инструменты

| Категория                | Инструменты и технологии                                      |
|--------------------------|---------------------------------------------------------------|
| Язык программирования     | Python 3.11                                                   |
| Фреймворк тестирования    | `pytest`                                                      |
| HTTP-клиент              | `httpx` (асинхронный)                                         |
| Среда выполнения         | Docker, Docker Compose                                        |
| Управление зависимостями | Poetry                                                        |
| CI/CD (локальный)        | Ручной запуск тестов через контейнер                         |
| Система контроля версий  | Git + GitHub                                                  |
| Документация API         | Swagger UI (`/docs`)                                          |

Особое внимание уделено **изоляции тестовых данных**: каждый тестовый запуск использует отдельную транзакцию, откатываемую после завершения теста, что гарантирует независимость и идемпотентность.

## 5. Полученный опыт и рефлексия

Работа над *to_do_app* стала для меня первым полноценным опытом участия в **full-stack командной разработке** с чётким распределением ролей.

### 5.1. Профессиональный рост
- Освоила **практические аспекты тест-дизайна**: эквивалентное разбиение, граничные значения, анализ потока данных.
- Получила опыт работы с **асинхронным API-тестированием**, что ранее оставалось в области теории.
- Углубила понимание **жизненного цикла задачи** в Agile-подобной среде: от постановки — к реализации — к верификации.

### 5.2. Командное взаимодействие
Несмотря на отсутствие формального трекера задач (например, Jira), команда эффективно использовала **GitHub Issues и прямую коммуникацию**. Это позволило оперативно согласовывать поведение API и устранять расхождения между ожиданиями и реализацией.

### 5.3. Личные вызовы
Как специалист с преимущественно аналитическим и фронтенд-ориентированным бэкграундом, я столкнулась с необходимостью быстро освоить backend-стек (FastAPI, SQLAlchemy, Alembic). Это потребовало дополнительных усилий, но одновременно расширило мой технический кругозор и укрепило уверенность в работе с full-stack проектами.
