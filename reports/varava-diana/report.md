# Отчёт по участию в командном проекте To‑Do App
## 1. Моя роль
В командном проекте по разработке To‑Do приложения на FastAPI моя роль заключалась в реализации функциональности работы со списком задач на стороне бэкенда.
Я отвечала за добавление в API возможностей пагинации, фильтрации и сортировки задач, а также за согласование этих изменений с существующей моделью данных и CRUD‑слоем.

## 2. Мои задачи и выполненная работа
### 2.1. Расширение модели задачи
- Проанализировала исходную модель Task и требования задания (сортировка по приоритету и сроку выполнения).
- Добавила в модель Task в app/models/task.py новые поля:
  - priority: Integer — целочисленный приоритет задачи с значением по умолчанию 0.
  - due_date: DateTime — срок выполнения задачи, опциональное поле.
- Обновила Pydantic‑схемы в app/schemas/task.py:
  - Включила priority и due_date в базовую схему TaskBase, чтобы эти поля могли передаваться при создании и чтении задач.
  - Добавила эти поля в TaskUpdate для частичного обновления задачи.
  - Обеспечила корректную работу схемы TaskOut с учётом новых полей.

### 2.2. Доработка CRUD‑логики для задач
Изменила модуль app/crud/task.py, расширив функцию получения списка задач:
- Добавила параметры skip, limit для пагинации.
- Реализовала фильтрацию по:
  - статусу выполнения (is_completed),
  - идентификатору категории (category_id).
- Реализовала сортировку по:
  - приоритету (priority / -priority),
  - сроку выполнения (due_date / -due_date).
- Обновила функции create_task и update_task, чтобы они корректно работали с новыми полями:
  - При создании задачи теперь сохраняются priority и due_date.
  - При обновлении задаются только те поля, которые действительно переданы в запросе, включая новые атрибуты.

### 2.3. Расширение API эндпоинта для списка задач
Доработала роутер app/api/task.py:
- В эндпоинт GET /tasks/ добавила query‑параметры:
  - skip и limit — для пагинации.
  - status — фильтрация по выполненным / невыполненным задачам.
  - category_id — фильтрация по категории.
  - sort_by — выбор направления сортировки по приоритету или сроку выполнения.
- Настроила валидацию параметров с помощью fastapi.Query (ограничения на диапазоны и текстовое описание параметров).
- Обеспечила передачу всех параметров в слой CRUD, чтобы логика выборки была централизована.

### 2.4. Участие в командной интеграции
- Согласовала изменения в модели Task с другими участниками, отвечающими за авторизацию, категории и миграции.
- Следила за тем, чтобы мои изменения не затрагивали конфигурацию проекта (pyproject.toml, Docker, Alembic‑миграции), чтобы не создавать конфликтов на уровне инфраструктуры.

## 3. Использованные технологии и инструменты
1) Язык программирования: Python.
2) Веб‑фреймворк: FastAPI (реализация REST‑эндпоинтов и зависимостей).
3) ORM и работа с БД: SQLAlchemy (описание модели Task, запросы с фильтрацией, сортировкой и пагинацией).
4) Pydantic: описание и валидация входных и выходных схем (TaskBase, TaskCreate, TaskUpdate, TaskOut).
5) СУБД: PostgreSQL (используется в проекте через Docker‑контейнеры).
6) Система управления версиями: Git, работа с удалённым репозиторием на GitHub.

## 4. Саморефлексия и выводы
1. Реализовала важный для пользовательского опыта функционал: пагинацию, фильтрацию и сортировку задач, что делает API удобным для реального фронтенда и интеграций.
2. Аккуратно расширила модель данных и схемы, не ломая существующие эндпоинты и не вмешиваясь в чужие области ответственности (авторизация, темы, интеграция с внешними сервисами).
3. В начале проекта было сложно разобраться в общей структуре репозитория и распределении ролей: какие файлы относятся к моей задаче, а какие — к работе других участников. Постепенно эта проблема решилась за счёт чтения README, обсуждений в командном чате и анализа существующего кода.
4. Проект помог увидеть, как разные роли (авторизация, задачи, интеграция с внешними API, тестирование, DevOps) соединяются в одно целое приложение.
В целом участие в проекте дало полезный практический опыт backend‑разработки на FastAPI и совместной работы в одной кодовой базе.
